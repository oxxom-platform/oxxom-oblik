# Кабінет і керування працівниками

15 листопада 2026 року. Наступний блок етапу AUTH/ACCESS.

## Використання

Після оновлення зупиніть старий сервер Ctrl+C і запустіть з кореня проекту
`sh scripts/start-core.sh`. Скрипт застосує accounts.0004 та запустить 52 тести.
Відкрийте http://127.0.0.1:4180/app/. Для першого відвідування потрібен вхід з 2FA.
На сторінці успішного входу тепер є посилання «Перейти в робочий кабінет».

Організацію вибирають зі списку доступних. Власник бачить працівників,
форму додавання та історію змін; інші ролі — назву організації та свою роль.
Довідники, документи й склад залишаються наступними етапами.

Власник може:

- Створити нового працівника з email, початковим паролем та роллю зі списку.
  Пароль перевіряється валідаторами Django. Працівник при першому вході
  налаштовує власний TOTP. Передавайте пароль особисто захищеним способом.
- Додати наявний акаунт за email. Глобальні пароль та ім’я при цьому не змінюються.
- Змінити роль, відкликати або відновити членство в поточній організації.
  Доступ до інших організацій зберігається. Останнього активного власника
  не можна відкликати чи понизити; спочатку призначають іншого.
- Переглядати історію успішних змін доступу: хто, коли, до кого й що змінив.

Під час невдалого додавання форма зберігає введені дані. Пароль не повертається
через API та не записується в журнал. Списки працівників і подій мають пагінацію
по 50 записів. Усі імена й email відображаються як текст, а не HTML.

## API та захист

- GET /api/v1/organizations/{organization_uuid}/members
- POST /api/v1/organizations/{organization_uuid}/members/add
- POST /api/v1/organizations/{organization_uuid}/members/{membership_uuid}
- GET /api/v1/organizations/{organization_uuid}/access-events

Кожен маршрут потребує завершеної MFA-сесії та права members.manage саме
в зазначеній організації. Відомий чужий UUID і прапорець superuser не дають
доступу. Членство шукається одночасно за organization_uuid та membership_uuid.
POST вимагає CSRF. Усі операції зміни блокують рядок організації в PostgreSQL,
повторно перевіряють право всередині транзакції та атомарно записують подію.
Це захищає останнього власника від двох одночасних взаємних відкликань.

Історія AccessEvent не має HTTP-маршрутів редагування/видалення. Посилання
на організацію, діяча та членство захищені PROTECT. Глобальне блокування
акаунтів, зміна чужого пароля і скидання чужого TOTP через цей кабінет не надаються.

## Перевірки та міграція

Загальний набір: 52 тести. На тимчасовій SQLite 50 пройшли, 2 пропущено. Перевірено сценарії
авторизації й керування членством, ізоляція, CSRF, атомарність створення,
заборона зміни останнього власника та негайний відгук прав. Два конкурентні
тести призначені для PostgreSQL і пропускаються на SQLite: споживання одного
TOTP двома запитами й взаємне відкликання двох власників.

Остаточна перевірка на PostgreSQL та ручне приймання інтерфейсу потрібні
на Mac користувача. Робоча конфігурація PostgreSQL не змінена. JavaScript
екрана входу й кабінету перевірено через node --check.

Міграція accounts.0004 додає лише таблицю AccessEvent. Для відкоту коду
таблицю зберігають. Зворотна міграція видаляє історію доступу, автоматично її
не виконують. Створення першого власника адміністративною командою не має
події AccessEvent; повний журнал автентифікації та контрольоване скидання
2FA залишаються незавершеними задачами етапу 2.
