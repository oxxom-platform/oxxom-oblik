## Реалізація

- `/demo/`, `/en/demo/`, `/ru/demo/`, `/cs/demo/`: мова URL має пріоритет над
  cookie й зберігається для переходу в робочий простір.
- Композиція погодженого макета, чинний графічний логотип і UI, реальні tokens
  `--ink:#0c2c23`, `--muted:#596a65`, `--green:#008963`, `--accent:#00a878`,
  `--line:#e1e9e5` з landing.css. Нову палітру не запроваджено.
- CTA головної ведуть на форму; інтерактивна ілюстрація на лендингу залишається.
  Контакт `info@oxxom.com.ua` є в публічних футерах головної та форми.
- Поля з прикладовими значеннями readonly та без `name`: браузер їх не надсилає.
  Навіть підроблений POST з реальним ім’ям/email/телефоном не змінить fixture.
  Зберігаються лише фіксовані тестові значення, UUID, час, код мови й product.
  Немає збереження IP, User-Agent, UTM чи довільних коментарів відвідувача.
- Форма явно позначена тестовою. Немає вигаданих реквізитів ТОВ, фіктивної
  політики, автоматично проставленої згоди чи обіцянки заброньованого часу.
- UI має idle/submitting/success/error/rate-limited, видимий номер тестової
  заявки, захист подвійного кліку й зрозуміле повідомлення при старому ticket.
- Немає сторонніх трекерів. Локальна DOM-подія успіху містить тільки product,
  mode і status. Сторонні analytics-події не додаються до появи consent-політики.

## Зберігання й захист

Новий додаток `demo_booking`, три нові таблиці: synthetic requests, mail outbox,
global test throttle. Міграція не змінює існуючі бізнес-таблиці.
Підписаний UUID-ticket живе одну годину; повтор того самого ticket повертає
попередній receipt і не створює повторний mail job. CSRF/Origin обов’язкові.
До CSRF-розбору API допускає лише URL-encoded POST з Content-Length до 4096
байтів; multipart/file uploads та завеликі запити відхиляються без парсингу.
Сторінки працюють без запитів до БД; API має мінімальну публічну дію без доступу
до користувачів, організацій чи фінансових записів.

Прототип обмежено 20 новими тестами на хвилину загалом і 500 записами. Це
навмисно глобальне обмеження без збереження адрес відвідувачів. Досягнення
місткості призупиняє нові тести, не видаляє квитанції чи історію доставки.
Немає GET/list/detail API для читання заявок. Відповідь містить тільки UUID і
локалізований текст. POST-значення позначені sensitive; у коді немає їх логування.

Тестова сторінка noindex/nofollow, no-store, canonical/hreflang. У sitemap вона
не додається. У CSP script-src дозволяє лише власні файли; inline styles
допускаються для наявної статичної ілюстрації. Обмеження iframe/object/base
та form-action зберігаються. Чинні MFA-сесії не перериваються й не подовжуються.

## Поштова частина

Публічне натискання записує заявку та outbox однією транзакцією. Сам HTTP-запит
не звертається до SMTP. У цій версії немає автоматичного mail timer:
без окремого налаштування листи не надсилаються. UI повідомляє про отримання
тестової заявки, не про доставку листа чи бронювання зустрічі.

Команда `deliver_demo_mail --dry-run` показує тільки технічні лічильники.
Ручний тест `deliver_demo_mail --limit 1` можливий після налаштування:

| Environment | Значення |
|---|---|
| `OXXOM_DEMO_TEST_SMTP_ENABLED` | `true` лише для погодженого ручного тесту |
| `OXXOM_DEMO_SMTP_HOST` | Фактичний корпоративний SMTP |
| `OXXOM_DEMO_SMTP_PORT` | Порт сервера, за замовчуванням 587 |
| `OXXOM_DEMO_SMTP_SECURITY` | `starttls` або `tls`; plaintext не підтримується |
| `OXXOM_DEMO_SMTP_USER` | Дозволений SMTP-акаунт |
| `OXXOM_DEMO_SMTP_PASSWORD` | Secret лише в захищеному server environment |

Адресат і From фіксовані: `info@oxxom.com.ua`; тема починається
`[OXXOM ОБЛІК][TEST]`, тіло містить тільки fixture та test request ID. Для From
потрібен дозволений корпоративним сервером відправник. Клієнт не задає headers,
recipient чи Reply-To. Конфігурація HUB/бекапів не використовується і не змінюється.

Job захищається PostgreSQL row lock/lease, Message-ID стабільний. Явна тимчасова
відмова SMTP дає backoff до п’яти спроб; постійна — failed. Timeout, невідомий
результат або протермінований sending lease — uncertain, без автоматичної
повторної відправки. Такі випадки потребують перевірки оператором: SMTP не
гарантує exactly-once, навіть зі стабільним Message-ID. Реальна доставка на
корпоративний сервер поки не перевірена; unit-тести використовують locmem/mock.

## Перевірки

[CI 44152691399](https://github.com/oxxom-platform/oxxom-oblik/actions/runs/44152691399).
`makemigrations --check --dry-run`: No changes detected. Окремо 6 updater tests
PASS, а існуюча перевірка error responses/Nginx також PASS.
Попередній pinned archive перевірено до фінального body-limit guard;
фінальний archive повторно перевіряється перед командою встановлення. Фінальна поведінка mobile menu: open/close, aria-expanded, Escape і повернення фокусу — PASS у Chromium.

- Синтетичні дані, підроблені поля, CSRF/Origin, honeypot, ticket/expiry,
  idempotency, глобальний throttle, місткість та атомарність request/outbox.
- Два PostgreSQL concurrency-сценарії: один nonce → один request/job;
  паралельні mail workers → один claim.
- SMTP mock/locmem: фіксований адресат/header, disabled/dry-run, backoff,
  uncertain після timeout/crash, відсутність секретів у станах.
- Чотири мови, спадкування мови, canonical/noindex, footer email, CTA,
  відсутність DB-залежності GET і збереження семиденної MFA-сесії.
- Ізольований Chromium: 320/390/768/1024/1440/1920 px × чотири мови,
  логотип, кнопки, mobile menu, успішна відправка, 503/retry і double click.
- Guarded updater: checksum/allowlist, pinned helper, DB dump, credentials
  поза argv, відмова backup до запису файлів, rollback коду зі збереженням dump.

## Випуск на Ubuntu

`deploy/ubuntu/update-demo.sh ПОВНИЙ_SHA` завантажує конкретний переглянутий
реліз. Installer дозволяє 22 runtime-файл, перевіряє baseline восьми існуючих
файлів SECURITY-01A та SHA256 нових. Невідома серверна правка зупиняє оновлення.
Механізм файлового rollback повторно використовує checksum-pinned guard
попереднього випуску; довільний код з архіву не імпортується.

Перед записом коду створюються приватні `before.dump`, копія app.env, оригінали
файлів і receipt. `pg_restore --list` перевіряє структуру dump; це не підміняє
ізольоване відновлення. Далі Django check, тільки додаткова міграція demo_booking,
restart сервісу Обліку й GET smoke головної/форми чотирма мовами, health/ready,
існуючих 404 HTML/JSON. Updater не створює тестову заявку і не надсилає email.

При відмові повертається код, нові demo-таблиці й receipts зберігаються. Вони
сумісні з поверненням попереднього застосунку й не видаляються автоматично.
Відновлення всієї production-БД не виконується автоматично, щоб не стерти
паралельні бізнес-операції. Recovery-каталог містить secrets/дані: не копіювати
його в Nginx, Git або публічні артефакти. NPM у цьому випуску не змінюється.

## Перехід до робочої форми

Окремий погоджений випуск після реквізитів юридичної особи та політики:
реальні контактні поля, E.164-валидація, затверджена правова підстава/retention,
поштова автоматизація, реальна SMTP/SPF/DKIM/DMARC перевірка й належна
адміністративна робота із заявками. Для цього прототипу live mode не існує:
одна environment-змінна не дозволить почати збір реальних контактів.

## Ubuntu: права нового пакета

Виправлено root/service regression установщика: нові каталоги пакета та
залишені після rollback каталоги мають root:oxxom 0750, нові файли —
root:oxxom 0640. Метадані існуючих бізнес-модулів та private backup не змінюються.
Каталоги готуються тільки після успішного dump; symlink відхиляється.
Django check і додаткова міграція запускаються від користувача сервісу oxxom
до restart. Окремий Linux CI-тест відтворює недоступний root:root 0750 пакет,
після виправлення імпортує його від непривілейованого користувача та
перевіряє, що цей користувач не може змінювати код.

## DEMO-ARROW-01 — підказка до форми

По центру першого екрана додано зелену стрілку вниз, яка вказує на форму.
Анімація використовує лише transform; prefers-reduced-motion вимикає її.
Посилання має назву мовою сторінки, доступне з клавіатури й переводить
фокус до форми з урахуванням закріпленого header. Це не кнопка «Нагору».

Окремий apply-demo-arrow.py змінює лише два наявні CSS/JS-файли, перевіряє
точні початкові/кінцеві hashes, зберігає оригінали й відновлює їх при відмові.
Fingerprint URL оновлюється під час запиту. Перезапуск сервісу, міграції,
зміни NPM, MFA та environment не потрібні.

збереження невідомих змін.
