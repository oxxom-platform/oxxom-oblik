# Ubuntu: розміщення та обслуговування

Актуально на 17.11.2026. Сервіс опубліковано за адресою
https://oblik.oxxom.com.ua/. Підтвердження й незавершені операційні завдання
зібрані в [PROJECT-STATUS](PROJECT-STATUS.md).

## Поточна установка

| Компонент | Розміщення |
|---|---|
| ОС | Ubuntu 24.04 LTS |
| Застосунок | Django під Gunicorn, окремий користувач служби |
| Керування процесом | systemd, служба `oxxom-oblik` |
| База даних | PostgreSQL 16 на VM застосунку |
| HTTPS | Окремий наявний Nginx Manager із сертифікатом домену |
| Код | `/srv/oxxom-oblik/app` |
| Python-оточення | `/srv/oxxom-oblik/venv` |
| Конфігурація | `/etc/oxxom-oblik/app.env`, з обмеженими файловими правами |
| Backend | Порт `4181`; адреси прослуховування та довіреного проксі задає серверний профіль |

Проксі передає Host і фактичну зовнішню схему. Gunicorn приймає HTTPS-заголовки
від налаштованих довірених джерел. Мережеві адреси та секрети конкретної
інсталяції до цієї інструкції не додаються.

## Перевірка на VM

Стан служби:

```sh
sudo systemctl status oxxom-oblik --no-pager
```

Процес і готовність БД перевіряються окремими endpoint-ами. Для локального
backend-запиту з VM зберігайте домен і зовнішню HTTPS-схему:

```sh
curl --fail --silent --show-error --connect-timeout 3 --max-time 10 \
  -H 'Host: oblik.oxxom.com.ua' \
  -H 'X-Forwarded-Proto: https' \
  http://127.0.0.1:4181/api/v1/health

curl --fail --silent --show-error --connect-timeout 3 --max-time 10 \
  -H 'Host: oblik.oxxom.com.ua' \
  -H 'X-Forwarded-Proto: https' \
  http://127.0.0.1:4181/api/v1/ready
```

`health` перевіряє процес. `ready` повертає успіх за доступної БД та відсутності
незастосованих міграцій. Окремо перевіряються публічний HTTPS, вхід із MFA
та робочий сценарій документа. Успіх loopback-запиту підтверджує лише відповідну
частину шляху до застосунку.

## Оновлення

Установлений код — розпакований архів закріпленого коміту GitHub, а не Git checkout.
Оновлення готують як окремий перевірений реліз із резервною копією, перевірками
сумісності та способом повернення попереднього коду.

Для вже встановленого SEO-01 існує спеціальний сценарій
[`update-seo.sh`](../deploy/ubuntu/update-seo.sh). Він застосовує лише
визначений manifest-ом набір файлів, перевіряє контрольні суми, створює свіжу
резервну копію, перезапускає застосунок і виконує контрольні запити.
Його призначення — цей конкретний реліз; подальші зміни потребують власного
пакета та перевірки сумісності.

Попередні файли SEO-релізу й журнал підготовки зберігаються в закритій папці
`/srv/oxxom-oblik/update-backups/`. Дані робочої БД цей реліз не відновлює
і міграцій не виконує.

Інструкції початкового перенесення описують стан на момент міграції. Повторна
ініціалізація VM або первинне відновлення дампу не є способом оновлення
працюючої системи.

## Резервні копії

Підтверджені зашифрована копія на окремому Windows-сервері та її перевірене
відновлення в ізольовану тестову БД. Дані та ключі відновлення зберігаються
в різних зашифрованих Restic-сховищах із різними паролями.

Паролі сховищ і SMB-облікові дані залишаються на сервері з обмеженим доступом.
Власник зберігає засоби відновлення також поза VM і сервером резервних копій.
Підтвердження виконаних перевірок розміщені в серверних звітах:

- `/var/lib/oxxom-oblik-backup/first-success.json`;
- `/var/lib/oxxom-oblik-backup/restore-success.json`.

Автоматичний розклад, retention, повідомлення про збої та монтування після
перезавантаження ще потребують налаштування й приймання. Підтверджені ручні
перевірки не встановлюють виміряних RPO/RTO для повної втрати VM.
