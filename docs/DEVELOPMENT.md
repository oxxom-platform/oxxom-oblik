# Локальна розробка OXXOM OBLIK

Цей документ описує середовище розробки. Поточну Ubuntu-установку
обслуговують за [DEPLOYMENT](DEPLOYMENT.md); стан продукту —
у [PROJECT-STATUS](PROJECT-STATUS.md).

## Вимоги

- Python 3.11 або новіший.
- Docker із Compose та доступ до PostgreSQL 16 у локальному контейнері.
- Доступ до PyPI для першого встановлення залежностей.
- Node.js для окремих JavaScript-перевірок, що використовують `node:test`.

Сценарій запуску сформовано для локальної розробки на macOS. На Ubuntu
розміщений сервіс використовує окремі Python-оточення, PostgreSQL і systemd.

## Запуск

Із кореня репозиторію:

```sh
sh scripts/start-core.sh
```

Сценарій створює приватний `.env`, якщо його немає, і зберігає наявну
конфігурацію. Окремий ключ MFA створюється в `.secrets/mfa.key`.
Значення секретів не виводяться. Далі встановлюються залежності, запускається
PostgreSQL, перевіряються конфігурація та міграції, виконуються інтеграційні
тести на окремій тестовій БД і запускається Django на loopback.

| Адреса | Призначення |
|---|---|
| `http://127.0.0.1:4180/` | Публічний лендинг українською |
| `http://127.0.0.1:4180/en/`, `/ru/`, `/cs/` | Інші мовні версії |
| `http://127.0.0.1:4180/login/` | Вхід і MFA |
| `http://127.0.0.1:4180/app/` | Робочий простір після входу |
| `http://127.0.0.1:4180/api/v1/health` | Стан процесу |
| `http://127.0.0.1:4180/api/v1/ready` | Доступність БД та відсутність очікуваних міграцій |

За замовчуванням віртуальне оточення створюється в `~/OXXOM-Dev/venv`,
поза директорією вихідного коду. Інший шлях можна передати через `OXXOM_VENV`.
Django запускається з `--noreload`: після зміни коду його потрібно перезапустити.

Першого власника створюють командою `create_owner`; параметри доступні через:

```sh
"$HOME/OXXOM-Dev/venv/bin/python" backend/manage.py create_owner --help
```

Власник надає доступ працівникам через робочий інтерфейс. Для входу до даних
потрібно завершити налаштування TOTP та зберегти одноразові резервні коди.

## Перевірки

Команди нижче використовують стандартний шлях віртуального оточення.
Якщо задано `OXXOM_VENV`, використовуйте Python із цього оточення.

```sh
"$HOME/OXXOM-Dev/venv/bin/python" backend/manage.py check
"$HOME/OXXOM-Dev/venv/bin/python" backend/manage.py makemigrations --check --dry-run
"$HOME/OXXOM-Dev/venv/bin/python" backend/manage.py test accounts core catalog documents inventory posting operations payments reports printing catalog_imports --noinput
```

Для повного інтеграційного набору потрібен локальний PostgreSQL і право
створення окремої тестової БД. PostgreSQL-перевірки охоплюють транзакції та
конкурентні сценарії; запуск на SQLite не замінює їх.

Публічні налаштування мови та спільні налаштування інтерфейсу:

```sh
node --test tests/public-ui.test.mjs tests/ui-preferences.test.mjs
```

Інші сценарії перевірок описані в документах відповідних модулів.
Історичні звіти фіксують конкретні прогони; вони не є поточним CI-бейджем.

## Мови та ресурси

Каталог інтерфейсу — `backend/core/locale/ui.json`. Після його зміни
оновіть JavaScript-словник:

```sh
python3 scripts/build-ui-locales.py
```

Публічний лендинг отримує окремо локалізований HTML і невеликий набір даних
демонстрації. Мовні URL, метадані та ресурси описані в `backend/core/seo.py`.
Дані довідників, назви організацій і введені користувачем тексти не перекладаються
як службові написи інтерфейсу.

## Дані та Git

`.env`, ключі MFA, дампи, робочі БД та приватні пакети перенесення залишаються
поза Git. Перед публікацією коміту перевіряють індекс і запускають:

```sh
"$HOME/OXXOM-Dev/venv/bin/python" -u scripts/check-git-content.py
```

Перевірка відхиляє приватні шляхи та відомі локальні секрети. Вона не замінює
перегляду змін і не перевіряє невідомі секрети в усій історії репозиторію.

Зупинка локального вебсервера — `Ctrl+C`. PostgreSQL можна зупинити командою
`docker compose stop db`, яка зберігає наявний volume із даними.
