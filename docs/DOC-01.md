# Чернетки продажів DOC-01 / DOC-02

Оновлення: проведення та залишки додано наступним блоком, див. POST-01.md. Нижче описано попередній етап чернеток; його твердження про відсутність проведення стосуються стану до POST-01.

15 листопада 2026 року. Етап 4, локальна розробка.

## Запуск і сценарій приймання

Після Ctrl+C у терміналі вебсервера, з кореня проекту:

```sh
sh scripts/start-core.sh
```

Скрипт застосовує documents.0001 і перевіряє accounts, core, catalog, documents.
Відкрийте http://127.0.0.1:4180/documents/ або «Документи продажу» у кабінеті.

У довідниках підготуйте контрагента, склад, послугу з одиницею «год» і ціною
1500.00 та товар з одиницею «шт» і ціною 100.00. Створіть продаж, виберіть
контрагента й склад. Додайте послугу 2 × 1500.00 і товар 3 × 100.00.
Збережіть чернетку: остаточна сума має дорівнювати 3300.00 грн.
Оновіть сторінку або повторно увійдіть та відкрийте її зі списку.

Перевірте зміну кількості/ціни, додавання/видалення та переміщення рядків.
Відкрийте документ у двох вкладках: збереження застарілої версії має дати
409 і залишити введену форму. Перед повторним збереженням потрібно відкрити
актуальну версію зі списку та перенести потрібні зміни.

## Реалізована поведінка

- Одна організація на документ. Контрагент, склад, товар/послуга — лише зі
  списків цієї організації; ручних назв позицій і одиниць у документі немає.
- Дата, примітка до 2000 символів, від 1 до 100 упорядкованих рядків.
- Кількість > 0 з точністю до 3 знаків; ціна >= 0 з точністю до 2 знаків.
  Кількість: до 999999999.999; ціна: до 999999999999.99 UAH.
- Decimal на сервері, ROUND_HALF_UP кожного рядка до копійок і підсумок
  округлених рядків. Клієнтські суми/статуси/назви ігноруються.
  Інтерфейс попередньо рахує суму через BigInt, без binary float для грошей.
- Знімки назви/типу позиції, назви/позначення одиниці, ціни та реквізитів
  контрагента, назви складу. Зміна довідника не змінює збережений документ.
- При редагуванні тієї самої позиції за тим самим UUID рядка знімки
  зберігаються; зміна ціни й кількості явна. Нова позиція бере актуальні
  назви/одиницю з довідника. Аналогічно для контрагента та складу.
- Раніше вибрані архівні записи можна зберегти в наявній чернетці;
  нові архівні записи вибрати не можна. Для товарного рядка склад обов’язковий.
- UUID і номер РЛ-рік-послідовність, унікальний в організації/році для
  продажів. Зміна року дати видає новий номер нового року; старий номер
  не використовується повторно. Інші типи документів ще не реалізовані.
- Збереження перевіряє version. Блокування організації/документа, номер,
  шапка, рядки й подія аудиту змінюються в одній транзакції.
- Чернетки можна копіювати, архівувати й відновлювати. Копія отримує новий
  UUID/номер, поточну дату Europe/Kyiv і поточні знімки активних довідників;
  кількості, ціни та примітка переносяться з джерела. Архівні посилання
  потрібно відновити в довідниках до копіювання. Історія джерела не змінюється.
- Пошук за збереженим ім’ям контрагента/приміткою, фільтр стану і пагінація 50.

Це чернетки: проведення, оплати, борги та складські рухи не створюються.
Після помилки форма не очищується. Повторне редагування у списку завантажує
поточну версію. Закриття форми або зміна організації скидає незбережену форму.

## Доступ і API

Власник, бухгалтер і менеджер читають та змінюють чернетки. Спостерігач читає.
Комірник не отримує продажі, ціни та контрагентів через API документів.
Кожен запит вимагає MFA, активного членства й активної організації.
POST використовує JSON і CSRF; числа quantity/price передаються рядками.

База: /api/v1/organizations/{organization_uuid}/documents.

- GET база: status=active/archived/all, q, page.
- POST /add: date, counterparty UUID, warehouse UUID/null, note, lines.
- GET /{uuid}: шапка і рядки зі знімками та version.
- POST /{uuid}/save: ті самі поля та version. Для існуючих рядків — id.
- POST /{uuid}/state: version, is_active (JSON boolean).
- POST /{uuid}/copy: version джерела.

Рядок: product UUID, quantity, price, опційно id з поточного документа.
Чужий, невідомий або повторний id рядка відхиляється. Перестановка визначається
порядком масиву. Для нового рядка id не передається. Видалення HTTP DELETE
не надається. DocumentEvent зберігає діяча, організацію, документ, дію й версію.

## Перевірки і межі

19 функціональних тестів документів пройшли на тимчасовій SQLite: 3300.00 і нова сесія, відсутність ручних
позицій, half-up, незмінність знімків, редагування/порядок/видалення рядків,
чужі UUID та посилання, кількість/точність/типи, склад, версії, чужі id рядків,
архів/копія, архівні довідники, номери/рік/організація, ролі, атомарний відкат,
MFA/CSRF/заборона видалення, пошук і некоректні запити.
Два нові PostgreSQL-тести перевіряють конкурентне створення номерів і
одночасне редагування однієї версії. Разом з AUTH/ACCESS — чотири
конкурентні сценарії, які пропускаються на SQLite.

Повний набір містить 97 тестів. Допоміжні перевірки в середовищі агента
виконуються на тимчасовій SQLite; конфігурація робочої PostgreSQL не змінена.
Міграції узгоджені, JS перевірено node --check. Приймання PostgreSQL і реальний
браузерний сценарій потрібні на Mac. Вибір позицій зараз завантажує активні
довідники посторінково; продуктивність селекторів на пілотних обсягах ще
потребує вимірювання. Навантажувальне приймання не виконувалося.

Міграція додає таблиці документів, рядків, послідовностей та аудиту. Відкат
коду залишає їх на місці. Зворотна міграція видаляє документи й історію,
автоматично її не виконують. Далі — проведення, рухи складу та собівартість
після погодження алгоритму з бухгалтером. Український інтерфейс не означає
готову податкову/регламентовану друковану форму.


## Виправлення порожнього списку контрагентів

У формі продажу з’явилися «Додати контрагента» та «Додати склад» з окремим
діалогом створення запису довідника. Використовуються ті самі API,
організаційна ізоляція, права та аудит catalog; новий UUID автоматично
вибирається в документі. Не створюються вигадані клієнти або склади.
Менеджер може додати контрагента, але не склад; це визначається серверними
правами. Користувач без прав звертається до власника.

Для позицій є посилання в окрему вкладку довідника саме поточної організації
та кнопка «Оновити списки». Оновлення не змінює рядки, кількості, ціни,
дату, примітку та поточний вибір контрагента/складу. Поля документа,
створення та збереження захищені від повторного натискання на час запиту.
При помилці створення контрагента діалог і введена назва залишаються.
Виправлено повторну доступність кнопки збереження після операцій.

Перевірки цього виправлення: 43 Django-тести documents/catalog пройшли на
тимчасовій SQLite, 2 конкурентні тести documents пропущено для PostgreSQL.
Сценарій JavaScript перевірено з мінімальним DOM через V8: автоматичний вибір
нового запису, збереження полів/рядків, помилка створення, оновлення списків,
стан кнопки збереження та приховування кнопок для читача. Це перевірка логіки,
а не приймання справжнього браузера. Файл для повторного запуску через Node:
`node tests/test_document_lookups.js`. Синтаксис обох змінених JS перевірено V8.
Схема БД та серверні правила створення довідників не змінювалися.
