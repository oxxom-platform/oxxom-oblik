# PRINT-01 — рахунок, накладна та акт

15 листопада 2026 року. Наступний блок після підтвердження роботи звітів.
Погоджений порядок збережено: функціональні блоки, потім спільна оболонка.

## Реалізована механіка

У картці збереженої реалізації з’являються посилання:

- «Рахунок / PDF» — усі рядки; доступний для збереженої чернетки та проведеної
  реалізації. Чернетка, архів і сторнований документ явно позначаються у формі.
- «Накладна / PDF» — тільки товари проведеної реалізації.
- «Акт послуг / PDF» — тільки послуги проведеної реалізації.
- «Реквізити організації» — налаштування власника/бухгалтера.

Для змішаного документа кожна форма підсумовує власні рядки: наприклад,
товарів 300 грн і послуг 3000 грн — рахунок 3300, накладна 300, акт 3000.
Послуги не додаються в накладну, товари — в акт. Порожня частина не друкується.
Номер і дата походять із реалізації; окрема нумерація друкованих копій не створюється.

Посилання відкриває захищену сторінку A4 у новій вкладці. Кнопка
«Друкувати / зберегти PDF» викликає системний діалог браузера. Серверний
PDF-рушій, нові Python-залежності та зовнішні шрифти не потрібні.
У друці приховуються кнопки, повторюється шапка таблиці, рядки й блок підсумків
не розриваються, довгі назви переносяться. PDF зберігає користувач у діалозі друку.

Друкується збережений документ. При незбережених змінах посилання заблоковані
з поясненням. У URL передається версія; застаріла версія повертає 409 замість
непомітного друку іншої редакції. Відсутність параметра version у прямому URL
означає поточну збережену редакцію. Невірні або повторені параметри відхиляються.

## Реквізити та історія

Сторінка /organization-details/: повна назва/ПІБ, тип зі списку, код,
адреса, банківські реквізити, email, телефон та необов’язковий ПІБ підписанта.
Початково немає вигаданих банківських реквізитів: форма пропонує лише чинну
назву організації, доки користувач не збереже власні дані.

Зміна дозволена власнику й бухгалтеру через окреме право organization.details.
Менеджер/спостерігач можуть читати реквізити та друкувати доступні їм продажі,
як і читати ціни цих продажів. Комірнику друк форм із продажними цінами недоступний.
Глобальний superuser без членства не отримує доступ. Чужі UUID й відкликане
членство не відкривають даних. API потребує MFA; збереження додатково CSRF.

Реквізити мають версію, оптимістичний захист і журнал до/після з користувачем
та часом. Нова чернетка та її перезбереження беруть актуальний знімок.
При проведенні знімок оновлюється до поточних реквізитів і фіксується в тій
самій транзакції з проведенням. Подальша зміна профілю не переписує проведені
документи зі знімком. Конкурентна зміна профілю та проведення використовують
спільне блокування організації, отже реквізити фіксуються цілою узгодженою версією.

Для старих реалізацій без знімка не вигадуємо історичні дані: форма бере
поточні реквізити й прямо позначає відсутність історичного знімка. Друк не
дописує їх у проведений документ і не змінює його версію. Неповні реквізити
також явно позначаються, без автоматичного підставлення тестових даних.

Назви, одиниці, кількості, ціни та контрагент беруться зі збережених знімків
документа, а не з оновлених довідників. Суми перевіряються на узгодженість;
неузгоджений документ не друкується як успішний. Усі текстові поля екрануються.
Кількість — 3 знаки, гроші — 2; підсумки Decimal, без binary float.

## Межі форм

Це локальні форми MVP без розрахунку ПДВ, електронного підпису та фіскалізації.
У формі зазначено «ПДВ не розраховано», а не твердження про податковий статус
організації. Фіскальний чек не видається. Не додаються вигадані договори,
печатки, підписи чи твердження про юридичне приймання. Поля підписів залишаються
для заповнення сторонами; ПІБ підписанта з профілю сам по собі не є підписом.
До реального пілоту реквізити, податкову модель та форми перевіряє бухгалтер;
за вказівкою власника це не блокує локальну реалізацію.

Друк не створює оплат або складських рухів і не змінює статус/версію реалізації.
Окремий PrintEvent фіксує відкриття попереднього перегляду: користувач, організація,
форма, документ, версія, джерело реквізитів, час. Це не підтвердження фізичного
друку або збереження PDF — браузер не надає такого підтвердження.
Повторне відкриття створює новий запис перегляду, але не дублює проведення.

## API та сторінки

- /organization-details/?organization=UUID — реквізити;
- GET /api/v1/organizations/{UUID}/issuer-profile — дані, version, configured, write;
- POST /api/v1/organizations/{UUID}/issuer-profile/save — поля профілю та version;
- GET /api/v1/organizations/{UUID}/issuer-events?page=1 — історія по 50 записів;
- GET /print/{organization_UUID}/{document_UUID}/{invoice|delivery|act}/?version=N.

HTML і API захищені сесією з MFA та серверною перевіркою організації.
Друк має no-store; файл логотипа публічний, не містить бізнес-даних і кешується
за окремою версією URL. Доступність кнопки не замінює серверної перевірки.

## Міграції та сумісність

- documents/0002_document_issuer_snapshot: JSON-знімок реквізитів, початково {}.
  Історичні реквізити старих документів не підміняються поточними.
- printing/0001_initial: IssuerProfile, ProfileEvent, PrintEvent.

Старі документи, суми та рухи зберігаються. start-core.sh застосує міграції
та включить printing у повні тести. Агент не мігрував робочу БД користувача;
для перевірок створювалися й видалялися окремі тестові бази.

Для майбутнього пілоту: перед міграціями бекап. Автоматичне видалення таблиць
або відновлення старої БД після нових записів заборонено. Відкат до старого
коду для запису без узгодження схеми не підтримується: старий код не знає
про обов’язкову JSON-колонку. При проблемі зупинити запис і випустити виправлення;
відновлення попереднього стану БД потребує окремого рішення про нові дані.

## Фактичні перевірки

Повний фінальний прогін на PostgreSQL: **211 тестів успішно, без пропусків**.
У тому числі всі попередні конкурентні перевірки продажів, повернень,
платежів та два нові сценарії профілю: пара одночасних змін однієї версії,
а також проведення під час зміни реквізитів. Тимчасова тестова БД видалена
штатним Django runner. Міграції узгоджені: No changes detected.
Журнал — PRINT-01-verification.txt. SQLite не використовується як доказ блокувань.

13 функціональних перевірок печатного блоку: профіль/версії/аудит/відкат,
ролі/MFA/CSRF/чужі документи, позначення чернетки, правильні підмножини й суми,
фіксація реквізитів при проведенні, поточний fallback старих документів,
відсутність тестових реквізитів, знімки назв/цін, Decimal, HTML-екранування,
застаріла версія, сторно, відсутня частина, неузгоджений підсумок та відмова аудиту.

JS з мінімальним DOM: версії профілю, збереження введеного при помилці,
read-only, запізніла відповідь організації; друк тільки збереженої версії,
три форми для змішаної реалізації, блокування незбережених змін, нова чернетка.
Попередні сценарії довідників, товарів, збереження та атомарного проведення
продажів/надходжень також пройшли. Повтор: node tests/test_printing_ui.js та
node tests/test_combined_ui.js. Мінімальний DOM не є браузерним прийманням.

Окремо в справжньому headless Chrome перевірено HTML/PDF на синтетичних
демонстраційних даних: рахунок 100 довгих рядків — 6 сторінок A4;
накладна 50 товарних рядків — 4 сторінки; акт 50 рядків послуг — 4 сторінки.
Зображення логотипа й українські тексти відображаються. Це перевірка макета,
а не приймання юридичної форми чи особистого принтера користувача.

## Приймання користувачем

1. Перезапустити start-core.sh, дочекатися міграцій і тестів.
2. Відкрити «Реквізити організації» та зберегти власні дані.
3. У картці реалізації відкрити рахунок, накладну або акт; зберегти PDF через друк.
4. Перевірити назви, кількості, реквізити й суми частин змішаного документа.
5. Змінити чернетку — друк має попросити збереження. Старі документи без знімка
   мають пояснення про поточні реквізити; нові проведені документи — знімок.

Наступний блок IMPORT-01: шаблони CSV, попередній перегляд, помилки рядків,
дублікати та явне підтвердження без автоматичного проведення.

## Останній логотип

За прямою вимогою власника повернуто **точний вихідний стилізований знак**
з upscalemedia-transformed (9)(1).png. Нові генерації зі звичайними літерами
не використовуються. Вихідний PNG збережено незмінним як oxxom-wordmark-source.png.
SVG-композиція oxxom-oblik-aligned.svg містить сам оригінальний растр і наявну
зелену плашку з білими літерами. Шрифт не підбирається й знак не перемальовується.
Білий фон вихідного растра не показується завдяки SVG-фільтру; чорне накреслення
та пропорції зберігаються. Компоненти пропорційно масштабовано за видимими межами:
обидва мають висоту 100 та верхню координату 6. Плашка більше не вища за знак.

Перевірено у Chrome і як локальний SVG, і як HTTP-ресурс із реальними CSP-заголовками
на кольоровому тлі: фон прозорий, обидва компоненти вирівняні. Новий ресурс
/assets/brand/oxxom-oblik.svg?v=20261115-original-aligned використовується в усіх
поточних екранах, включно з печатними формами. Старий PNG-маршрут збережений
для сумісності старих URL, нові сторінки його не використовують.
