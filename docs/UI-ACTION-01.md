# Одна дія: зберегти та провести

15 листопада 2026 року. Поліпшення механіки роботи, без об’єднання оболонки.

Користувач підтвердив проведення надходження після вибору постачальника,
окремого збереження та проведення; на залишках з’явився товар 1.000
вартістю 500.00. Три кроки виявилися неочевидними. Реалізовано єдину
основну дію для продажів, початкових залишків/надходжень і складських операцій.

## Нова механіка

- Основна кнопка власника/бухгалтера — «Зберегти та провести». Вона доступна
  і новому документу, і активній чернетці з незбереженими змінами.
- «Зберегти чернетку» — окреме другорядне збереження без рухів. Для ролі,
  яка не має права проведення, це єдина основна дія; після збереження є
  повідомлення передати документ власнику/бухгалтеру для проведення.
- Вибір постачальника, правка кількості/ціни та проведення більше не
  потребують проміжного натискання «Зберегти чернетку».
- Обидва етапи на сервері в одній транзакції: шапка, рядки, номер, аудит,
  проведення, баланс, рухи та ключ повтору. Якщо бракує товару, постачальника
  чи ціни, дата закрита або версія застаріла — жодні зміни запиту не
  зберігаються в БД. Введені дані залишаються в поточній формі.
- Під час запиту видно «Зберігаємо та проводимо…», повторне натискання
  заблоковано. Для повтору після невідомого мережевого результату в межах
  відкритої сторінки використовується той самий ключ і те саме тіло.
- Успішна відповідь відразу відображає проведений документ без додаткового
  обов’язкового завантаження довідників. Поля стають лише для читання,
  з’являються сторно та посилання на залишки поточної організації.
- Помилка перевірки 4xx пояснює, що документ не збережено й не проведено.
  При втраті підтвердження не стверджуємо, що сервер не виконав запит:
  пропонуємо повтор із захистом від дублювання.
- Результат і причина помилки показуються біля кнопок. Нативна помилка
  форми називає поле; закупівельна та продажна ціни залишаються різними.

Зміна не надає нових прав менеджеру/комірнику й не проводить чернетки
автоматично при звичайному збереженні. Проведений документ не можна
відредагувати або знову провести. Сторно — окрема явна дія.

## API

Нові маршрути відносно /api/v1/organizations/{organization_uuid}:

- POST /documents/save-and-post або /documents/{uuid}/save-and-post;
- POST /inventory/save-and-post або /inventory/{uuid}/save-and-post;
- POST /operations/save-and-post або /operations/{uuid}/save-and-post.

Тіло: {"document": {...поля відповідної чернетки...}, "idempotency_key":"UUID"}.
Для наявного документа в document обов’язкова актуальна version; для нового
UUID документа визначає сервер. Числа quantity/price передаються рядками.
Потрібні MFA, CSRF, право збереження відповідного типу та documents.post.

Ключ прив’язаний до організації, користувача, типу/UUID документа, дії та
повного тіла. Успішний повтор повертає початкову відповідь. Інше тіло або
маршрут із тим самим ключем — 409. Невдалий запит ключ не резервує. Стара
API-дія /post для вже збереженого документа залишається доступною клієнтам;
основна кнопка інтерфейсу використовує нову атомарну дію.

## Перевірки

9 нових серверних сценаріїв пройшли на тимчасовій SQLite: нове надходження,
змінений постачальник без проміжного збереження, відсутній постачальник без
часткових даних/номера, нестача товару зі збереженням старої чернетки,
повтор нового документа з тим самим ключем, зміна тіла, продаж/повернення
однією дією, ролі, закритий період/помилка аудиту та застаріла/проведена версія.
Окремий PostgreSQL-тест перевіряє два одночасні повтори нового документа:
один документ, номер, проведення та рух. Він тут пропущений.

Загальний startup тепер містить 163 тести, 9 конкурентних потребують
PostgreSQL. Модулі posting/inventory/documents/operations перевірялися разом;
після виправлення ожидаемого значення у тестовій перевірці примітки
повторно виконано весь новий модуль: 9 пройшли, 1 пропущено. Реальна
PostgreSQL недоступна агенту. Повний запуск на Mac ще потрібний.

Синтаксис і логіка JS перевірені V8 з мінімальним DOM для всіх трьох екранів:
основна дія для нової/зміненої чернетки, повторний ключ, вибір постачальника
у тому самому запиті, пряме відображення відповіді, збереження доступних
варіантів складу, чернетка без проведення, стан тільки для читання та
посилання з правильною організацією. Реальне браузерне приймання ще потрібне.
Повтор: node tests/test_combined_ui.js. Схема БД не змінювалася цим блоком.

## Перевірка користувачем

Після перезапуску сервера відкрийте /inventory/, створіть надходження,
виберіть постачальника, склад, товар, кількість та закупівельну ціну.
Натисніть лише «Зберегти та провести». Перевірте статус «Проведено» і
перейдіть за посиланням до залишків. Для тесту відмови змініть продаж так,
щоб він перевищував запас: має залишитися стара версія в БД і введена
нова версія у формі з поясненням. Кнопка чернетки має зберігати без рухів.

Межа закритого періоду є окремим налаштуванням і не створює товарних рухів.
Об’єднання всіх екранів спільною оболонкою залишається останнім блоком,
як попросив власник; наступні функціональні блоки — гроші та звіти.
