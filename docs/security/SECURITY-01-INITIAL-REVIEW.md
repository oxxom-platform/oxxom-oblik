## F-01. Общий адрес прокси объединяет ограничения входа разных клиентов

**Статус:** воспроизведено в изолированной лабораторной среде.
**Production:** сценарий не запускался; фактическая цепочка источников требует
проверки на установленном сервисе.
**Приоритет:** проверить и исправить в первом блоке; предварительно высокий
риск доступности новых входов при описанной конфигурации. CVSS не назначен.

### Наблюдение по коду

[`auth_views.py`](../../backend/accounts/auth_views.py#L42) формирует ключи
`account:<identity>` и `source:<REMOTE_ADDR>`. Пять отказов за текущее окно
включают блокировку; достаточно одного заблокированного ключа. Та же логика
применяется к входу и MFA/перегенерации резервных кодов.

В рассмотренном профиле Gunicorn находится за отдельным прокси.
[`settings.py`](../../backend/config/settings.py#L14) не содержит middleware,
которое строит проверенный клиентский адрес из доверенной цепочки.
`forwarded-allow-ips` в профиле не является реализацией такого алгоритма
для `request.META['REMOTE_ADDR']`. Gunicorn документирует это значение
как адрес непосредственного соединения, обычно прокси.

### Лабораторное воспроизведение

Использованы Django test client, синтетический аккаунт, временный ключ MFA
и SQLite `:memory:`. Сетевых HTTP-запросов, обращения к production-БД
и блокировок настоящих пользователей не было. Адреса примеров относятся
к зарезервированным тестовым диапазонам.

В test client применено штатное отключение CSRF-проверки, чтобы отдельно
проверить логику rate-limit. Обход CSRF на живом сервере этим не подтверждается.
Успех 200 здесь относится к парольному шагу, а не к завершённой MFA-авторизации.

Клиенты имеют разные forwarded-адреса, но один TCP peer, как за общим прокси.
Сначала проверено, что верный пароль тестового B принимается. Затем другой
тестовый клиент делает пять неверных попыток для другого идентификатора.

| Проверка | HTTP |
|---|---|
| Верный пароль B до ошибочных попыток | 200 |
| Пять неверных попыток A через общий peer | 400, 400, 400, 400, 400 |
| Верный пароль B через тот же peer, иной forwarded-адрес | 429 |
| Тот же аккаунт B и верный пароль через другой peer | 200 |

Это воспроизводит совместное ограничение входа клиентов за одним адресом.
При соответствующей production-цепочке нарушитель может мешать новым входам
других пользователей. Уже действующие бизнес-сессии этим экспериментом
не проверялись и не объявляются заблокированными. Утечка данных, обход MFA
или захват аккаунта данным результатом не подтверждены.

### Требование к исправлению

Определить и проверить канонический клиентский адрес только через доверенную
границу. Прокси обязан контролировать заголовки; приложение должно различать
доверенный peer и произвольный прямой запрос, учитывать IPv4/IPv6 и правила
разбора цепочки. Простая замена на первый `X-Forwarded-For` создаёт обход лимита.

Сохранить независимые account/client ограничения, защиту от перебора и
контроль расхода ресурсов. Повторить T02/T03 на PostgreSQL и реальной схеме
прокси в тестовом окружении; production проверить ограниченным безопасным
способом без блокировки реальных аккаунтов.

## Что не выполнялось

Не менялись код приложения, настройки production, firewall, Nginx, SSH,
MFA-ключи, сроки сессий и рабочие данные. Не выполнялись сетевой перебор,
активная эксплуатация production, полный SAST/DAST/SCA или полный security-набор.
Лабораторная SQLite-проверка не заменяет проверку конкуренции PostgreSQL.
