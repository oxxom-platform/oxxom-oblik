# SECURITY-01B — відкликання інших сесій

18.11.2026. Статус: підготовлено до випуску; установку на Ubuntu ще не підтверджено.
Наступний прикладний блок після підтвердженого власником
`SECURITY-01B-REQUEST OK`. Відповідає відкритому пункту SEC-B03 попереднього аудиту.

Інвентар маршрутів оновлено: 119 декларацій, 78 tenant API.

## Поведінка

- «Безпека та резервні коди» відкриває керування без повторного парольного входу,
  якщо поточна MFA-сесія чинна. Кожна чутлива дія все одно потребує свіжого TOTP.
- `POST /api/v1/auth/sessions/revoke-others` обертає `User.security_stamp`,
  змінює ключ поточної сесії та зберігає її початкові `mfa_started` і дату завершення.
  Решта повних сесій і незавершених парольних challenge відхиляються при наступному
  зверненні. Уже виконаний запит не може бути скасований заднім числом.
- Перегенерація резервних кодів також обертає stamp і відкликає інші входи.
  Резервний або вже спожитий TOTP-код не може підтвердити ці дії.
- Перед споживанням фактора session hash повторно перевіряється під блокуванням
  рядка користувача. Запит, випереджений відкликанням, не може зберегти стару
  сесію під новим stamp. Транзакція охоплює TOTP, stamp і зміну поточної сесії.
- Застосовано CSRF, чинний MFA, перевірений auth source, обмеження невдалих спроб
  та `no-store`. Інші користувачі не зачіпаються. Міграції й нові залежності не потрібні.
- Інтерфейс перекладено українською, англійською, російською та чеською.
  Журнал `oxxom.security` містить тільки event/user_id/result після commit;
  пароль, email, OTP, cookies, MFA-секрет і recovery-коди в подію не передаються.
  Це не повний журнал усіх подій входу й не доставка сповіщень.

Нові тести охоплюють старі cookies, поточний абсолютний строк і ключ сесії,
інші акаунти, незавершений парольний challenge, повтор TOTP, recovery-код замість
TOTP, CSRF, прострочений MFA, невірний ключ шифрування, заміну recovery-кодів,
повторну перевірку stamp, rollback і відсутність секретів у події.
Окремий PostgreSQL-тест одночасних підтверджень пройшов у повному наборі.
Попередні SQLite-рядки залишені як історія локальної перевірки, не як доказ row locks.

Сумісність коду сесій перевіряється окремо із збереженою новішою базою
`16a844ed8efc857ca2b54a66daec55cf281eb232`, яка включає middleware лімітів
запитів. Сторінка приватного репозиторію в авторизованому Chrome 18.11.2026
показує цей самий коміт як останній у `main`. Після відновлення API-доступу
HEAD потрібно звірити повторно перед створенням гілки.

## Установка й відкат

`deploy/ubuntu/update-session-security.sh FULL_COMMIT_SHA` завантажує точний
перевірений реліз через налаштований GitHub CLI. Новий updater змінює тільки
дев’ять allowlisted файлів інтерфейсу й auth/config; SHA256 звіряються з пакетом
та встановленим request-limits baseline. Невідома серверна правка, symlink,
підмінений maintenance helper або archive member зупиняють установку.

Приватна recovery-копія з receipt зберігає оригінальні файли та їхні права.
Django check, імпорт нового handler і шаблону виконуються від `oxxom`.
Після restart перевіряються health/ready, чотири лендинги, login, branded errors
та HTTP 405 нового POST-only маршруту. Помилка відновлює всі попередні файли,
видаляє новий модуль і перезапускає попередню версію. Після раптового вимкнення
VM посеред запису потрібне ручне відновлення з recovery-копії.

Updater не виконує міграції, не змінює env, MFA-ключі, записи сесій, NPM і backup
автоматизацію. Відкликання сесій відбувається тільки після явної користувацької
дії зі свіжим TOTP. `SESSION_COOKIE_AGE` залишається 604800 секунд.

## Приймання

Зміни підготовлено від `main` 16a844ed8efc857ca2b54a66daec55cf281eb232.
Налаштований GitHub CLI має доступ до запису; окремий connector повертав 403
на створення гілки. Це обмеження підключення, не відсутність доступу власника.
У цій версії реєстр v5.0.0-7.4.3 позначає PASS тільки на прикладному source/test
рівні, з вимогою успішного CI; це не сертифікація ASVS або приймання production.

Перед установкою необхідні зелені PostgreSQL, dependency/history та updater
перевірки PR. Після установки перевірити двома браузерами: увійти в обидва;
у першому відкрити «Безпека та резервні коди» й використати новий TOTP для
«Вийти на інших пристроях»; перший вхід залишається, другий потребує нового
входу. Заміну резервних кодів перевіряти окремим наступним TOTP-кроком.

Повний ASVS-контроль і завершений production-аудит не оголошуються пройденими.
